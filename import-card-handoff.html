Import Card

Final class: .import-card (working name in the original spec was “Complete Card”). Shipped in @taxhawk-swoop/common. Prepared by Allison Baker (dev) · 2026-08-14 · sent back to Colton Bragg (UX) covering the Default and Uncategorized variants from the original spec, plus a new Failed variant the original doc didn’t define, and an existing Loading state carried over from the current product. Full compiled stylesheet: styles.css (the actual package build output, linked live below — not a snippet).

Purpose

Same purpose as the original spec, extended to cover the whole lifecycle of an uploaded file row, not just the ready-for-import moment: the Import Card now also represents a file that is still uploading and a file whose processing failed, in addition to the completed default/uncategorized states.

Open questions from the original doc — resolved

  • Final component name: .import-card, with modifier classes .uncategorized, .failed, and .loading toggled on the same root element (matches the “single base class + variant modifier” convention used elsewhere in the package).
  • Responsive breakpoint: built on the standard Bootstrap sm breakpoint (≥576px) — the mobile layout below applies under that, the desktop layout at/above it. No separate tablet treatment was needed.
  • “My Tax Files” link: shipped as a real inline <a> in the warning body copy; the microservice consuming this component sets the href, the component itself doesn’t hardcode a destination.
Palette drift resolved: the original mockup rendered the warning icon in #f79009, which wasn’t a SWOOP token. It shipped using $svg-warning / $icon-warning, which resolves to $warning-500 (#e49e1e) — the icon below is the token color, not the mockup’s hex.

Scope

  • The completed-upload card: file-type icon, filename, status line, form-type badge selector, remove button.
  • The uncategorized variant: warning surface plus attached explanation block, and the in-place transition between variants.
  • New: the failed variant, for files whose processing errored out — no icon-only content, so a Retry action replaces the badge.
  • Carried over: a loading variant for in-progress uploads, matching the same anatomy pattern (spinner in place of the icon, badge/remove hidden).
  • Desktop layout plus the 375px mobile layout defined below; in-between breakpoints inherit the desktop layout from sm (≥576px) up.

Behavior

  1. The badge opens a native form-type <select>. Changing the value updates the badge label immediately.
  2. Selecting Uncategorized converts the card to the warning variant and reveals the warning block; selecting any real form type converts it back. This is driven by a change listener in the package’s index.js that toggles the .uncategorized class — it wasn’t wired up yet when this spec was written, so it’s now shipped alongside the styles. (The examples above are wired up with the actual listener, jQuery included via CDN, so you can try it directly in this doc.)
  3. The remove button deletes the card from the list. No confirmation. (Also live above.)
  4. A failed card has no classification control — the retry badge sits in its place, styled and ready, but isn’t wired to a real retry action yet. It’s a planned feature, not a current one; today a failed upload has to be removed and re-added.
  5. The card itself is not clickable; only the badge/retry control and remove button are interactive.
  6. Every card renders the full markup up front — icon and error icon, both badges, the loading spinner, and the warning block are all present in the DOM for every state; the SCSS hides whichever ones don’t apply. This is a deliberate simplification of how the current live upload page works: that page’s JS sets style.display on each piece individually and wraps the card in an extra shell element to swap its border/background. This component collapses all of that down to one class (.uncategorized / .failed / .loading) on the root .import-card — no wrapper, no per-element JS, no inserting or removing child markup. The live page’s upload flow is being rewritten to drive this component instead of the other way around.

Accessibility, as shipped

  • The badge is a real <select> with an aria-label; focus shows the SWOOP ring per variant (see table above). The ring is bound to :focus-within on the pill wrapper, not just :focus-visible — the <select> is what actually receives focus, so :focus-visible alone on the wrapper never fired. Fixed during this build.
  • The warning block uses aria-live="polite" aria-atomic="false". It doesn’t carry the extra screen-reader context span other standalone alerts in the package use (“ - yellow warning message”) — the filename and status text right above it already give a screen reader user the context they need, so the redundant label was left off here.
  • Remove button: aria-label="Remove <filename>", icon marked aria-hidden="true".
  • All badge/retry text-on-surface pairs above meet 4.5:1.

Build notes

  • Shipped as a single component, src/scss/components/_import_card.scss, imported into _components.scss. One base class + variant modifiers (.uncategorized, .failed, .loading), matching package convention. Every child part (error icon, both badges, spinner, warning block) is styled display: none by default and switched on only by the modifier class that needs it — so consuming markup should always include all of them, not conditionally render a subset per state.
  • Icons use the SWOOP mask-image pattern (svg-mask-full mixin) — the file-type icons themselves (PDF/JPG/PNG/xlsx/csv) are pre-colored static assets, not mask-driven, so their purple/green fills are baked into the SVG rather than pointing at a token (there isn’t a primitive named for that exact purple/green pair — same as your handoff noted).
  • JS: the uncategorized-toggle listener now lives in the package’s index.js alongside the rest of the badge/dropdown DOM initialization. This page includes jQuery via CDN and runs that exact listener verbatim, plus the resize listener also in index.js and a demo-only remove button, so the examples above are actually interactive.
  • A progress overlay (.card-progress, rendered as a #progress-<id> div, first child of .import-card) was just added to visualize upload progress. It’s in the styles and test markup now; the JS that actually drives its width during an upload is still being built.

Do / Don’t

DoOne card per uploaded file, stacked oldest-first, 8px gap. Render the full markup — warning block included — for every card regardless of its current state, so a single class toggle can move it between states later.
Don’tConditionally omit the warning block (or spinner, or error icon) from a card’s markup based on its current state. It should always be there, just hidden by CSS until its modifier class is added.
